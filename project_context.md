# AI Workout Coach — Контекст проекта

Этот файл (`project_context.md`) предназначен для передачи контекста нейросетям. Он описывает текущую архитектуру, стек и логику работы Telegram Mini App для трекинга тренировок.

## 🛠 Технологический стек
* **Frontend:** Vanilla HTML, CSS (CSS variables, flex/grid), JavaScript.
* **Интеграция:** Telegram WebApp API (обработка кнопки "Назад", HapticFeedback).
* **Backend:** Python, FastAPI, Uvicorn.
* **База данных:** SQLite (асинхронное взаимодействие через `aiosqlite`).
* **AI Интеграция:** Библиотека `google-genai` (Google Gemini API).

## 📂 Архитектура и основные файлы
* `index.html` — единая точка входа (Single Page Application). Содержит всю разметку (календарь, модальные окна, таймер, анимацию лоадера со штангой) и клиентскую JS-логику.
* `backend/main.py` — инициализация FastAPI, раздача статики и подключение роутеров. Настроена авто-генерация таблиц БД при запуске (lifespan events).
* `backend/database.py` — настройка SQLite (файл `workout_app.db`), SQL-запросы для сохранения, получения и удаления тренировок.
* `backend/cardio_routes.py` (и роуты силовых) — эндпоинты API. Содержат логику формирования промптов и вызова Gemini API.

## 🧠 Логика AI-Ассистента
Для обхода жестких лимитов бесплатных квот (ошибки `429 RESOURCE_EXHAUSTED` на 20 запросов) и временных перегрузок серверов (`503 UNAVAILABLE`) реализована **система двойного фоллбэка**:
1. **Основная модель:** `gemini-3.8-flash` (высокий лимит запросов: 1500/день).
2. **Резервная модель:** `gemini-2.5-flash-8b` (включается, если основная перегружена).
3. **Заглушка (Hard Fallback):** Если обе модели недоступны, бэкенд не падает, а генерирует дефолтный JSON (`{"coach_notes": "Тренировка успешно сохранена! (AI-тренер временно недоступен)...", "next_workout": []}`), чтобы данные успешно записались в БД.
* **Парсинг:** Ответы от Gemini строго форматируются в JSON с помощью конфигурации `response_mime_type="application/json"`.

## 💾 База данных (SQLite)
В проекте используются минимум две основные таблицы:
* `strength_workouts`: Силовые тренировки (id, user_id, date, workout_data, created_at). В `workout_data` хранится JSON с массивом упражнений (веса, повторы, RPE), заметками атлета и разбором от тренера.
* `cardio_workouts`: Кардио сессии (id, date, subtype, distance_km, duration_sec, avg_pace, created_at).

## 🖥 Фронтенд и UI/UX
* **Календарь:** 
  * Маркеры дней: зеленые точки (силовая `has_strength`), красные точки (кардио `has_cardio`).
  * Для обхода агрессивного кэширования браузеров при работе через `ngrok` к GET-запросам календаря добавляется параметр `_t=${Date.now()}`.
  * Управление: короткий тап открывает тренировку/создание, долгий тап (long press) вызывает меню удаления.
* **Модальные окна:** При успешном удалении или сохранении окно принудительно закрывается (`closeModal()`), а календарь асинхронно перерисовывается (`loadMonthData()`).
* **Локальные черновики:** Несохраненные тренировки пишутся в `localStorage` (ключ `workout_draft_{user_id}`), кнопка "!" (draft alert) пульсирует в шапке, если есть черновик.
* **Таймер отдыха:** Встроен в окно редактирования, умеет работать в фоне и возвращаться к заданному времени.

## 🚧 Текущий статус и решенные проблемы
1. **Решено:** Бесконечные падения сервера из-за ошибок `503` и `429` от Gemini API. Внедрена обертка `try...except`, модели заменены на стабильную ветку `1.5-flash`.
2. **Решено:** Баг SPA с неудаляющимися зелеными точками. Добавлен сброс кэша (`_t=...`) и принудительное закрытие DOM-элементов.
3. **Решено:** Ошибка `no such table` в БД при удалении файла. Настроен `await database.init_db()` при старте сервера `uvicorn`. Фантомные записи удаляются прямыми SQL-запросами, а не полным сносом файла.
